## What this is

A React web application built on top of the Ivy Homes property API (Pune). Three demo users can log in, browse sale listings and rentals, explore builder projects, save listings, and open an insights dashboard. The assignment also asked for ten numerical answers about the Pune dataset and a list of everywhere the API documentation lies — both are in `submission.json`, generated by scripts, never hand-typed.

Every number in the submission is reproducible: `npm run verify` re-derives all ten answers from the snapshot in `data/raw/` and exits non-zero on any mismatch.

## The six things the brief required

1. **Login** — real `/auth/login`; session survives refresh (persisted token) and a pre-emptive `/auth/refresh` at expiry−60s keeps the app working far past the brief's 30 minutes. Token lifetime is actually **900s, not the documented 86400s**.
2. **Browse listings** — server-paginated grid (offset/limit, follows `has_more`); locality, BHK and furnishing filters hit the API.
3. **Listing detail** — every tile links to `/listings/:id`, reachable by URL, with decoded price, corrected area, the finding badges that apply, and a Google Maps link (geo coordinates exist on all records).
4. **Saved listings** — add/remove/list per account in `localStorage`, survives reload and re-login.
5. **Rentals & projects** — browsable with **correct prices and areas**: project prices decoded per the lakhs-below-₹1 Cr / crores-above rule, 306 sqm listings converted to sq.ft, rental `posted_at` read as the real UTC it is. Detail pages at `/rentals/:id` and `/projects/:id`.
6. **Insights** — `/v1/analytics/summary` is a documented 404, so the screen computes the same aggregates client-side from a full crawl and surfaces every discovery.

## How I investigated the documentation

**Step 1 — Test the API before writing any app code.** The first request, written exactly as the reference shows it, told me everything:

```
curl "https://solve.ivy.homes/v1/listings?limit=1&api_key=IVY26-XXXX"
# → {"detail":"send your key in the X-API-Key request header, not as a query parameter"}
```

The docs say `?api_key=`. The API corrects you with a helpful message. The error bodies turned out to be the single most reliable part of the document — from then on I read them as a map of the real API.

**Step 2 — Read every response field carefully.** Logging in immediately showed `access_token`, not `token`; `expires_in: 900` (15 minutes, not 24 hours); and a `refresh_token` + `refresh_url` — despite the docs stating "there is no refresh flow". That drove the interceptor design below.

**Step 3 — Pull the entire dataset first, then analyse.** Rather than reading records one at a time, I paged all three endpoints to `has_more=false` (~150 requests, ~2 min):

```
3,800 listings   (advertised total: 3,466)
1,450 rentals    (advertised total: 1,323)
  440 projects   (advertised total:   401)
```

The `total` understates every collection by a constant 8.8% — the scaled `total` finding.

**Step 4 — Form a hypothesis, then test the residual.** The first rule that fits fits most of the data; the answer lives in what it gets wrong.

- *Project prices are rupees* → falsified immediately: P30001 has `price_min: 80, price_max: 3.22`. The unit follows the **value** (lakhs below ₹1 Cr, crores at or above) — proven by the empty quadrant (zero crore-min/lakh-max records) and by `sort_by=price_max` ordering 22 lakh-quoted projects correctly by rupee value.
- *Listings are sq.ft everywhere* → 306 records serve square metres. The carpet/super ratio stays at 0.746 (both converted together), so I scored each record against the median carpet area for its own type + bedroom count: bimodal with an empty gap, low mode's median 0.0933 vs predicted 1/10.7639 = 0.0929. Clinched inside one building — Rohan Grand lists `carpet_area: 73` in magichomes vs 921/776/786 elsewhere; 73 × 10.7639 = 786.
- *Controls with many listings are suspicious* → wrong direction; that's just an agency line. The tell is many **names** on one number: 12 contacts carry 3–5 names each (a two-name contact does not exist), covering 320 fake listings priced at 0.6× the local median.
- *The endpoint filters out inactive listings* → it doesn't: 802 of 3,800 records are `is_live: false`.

| # | Key | Answer |

| 6 | `avg_price_per_sqft_2bhk` | **10844.99** (19042.07 without the sqm correction) |
| 7 | `costliest_project` | **P30288**, ₹4,47,00,000 — not the apparent ₹99.9 Cr |
| 8 | `listings_last_7_days` | **128** (115 if timestamps were wrongly read as UTC) |
| 9 | `fake_listing_ids` | **320** across 12 phone numbers |
| 10 | `projects_with_wrong_listing_count` | **95** of 440 |

Snippets of the reasoning:

- **Q2 — 3230 properties.** `listing_id` is unique (all 3,800), and lat/lng identifies a *building*, not a property — 247 coordinates carry several genuine flats. Matching on ten structural fields with area within 2% and coordinates within 200 m yields 570 re-listings. The count plateaus, not slides: carpet tolerance 0.98→0.80 gives the same 617 pairs, distance 200→1000 m the same 621; an independent name-based rule returns the identical 3230.
- **Q7 — P30288.** Decoded rupee values put every project at ₹5,300–11,000/₹sq.ft against a listing median of 10,334 — the documented reading puts 22 projects at ₹530,000–870,000/sq.ft. `P30394`'s `price_max: 99.9` is **99.9 lakh**, not crore.
- **Q8 — 128.** The naive timestamps are IST, not UTC: read as UTC, listings run 5.4 hours past the cap the honest rental timestamps respect.
- **Q9 — 320.** 12 numbers each carry 3–5 distinct `posted_by_name` values; 41.3% of these listings price below 0.6× the local median vs 0.7% of everything else — a 57× enrichment.

## What I checked that turned out to be fine

These hypotheses did not pan out; they matter as much as the ones that did.

- **Error bodies are genuinely useful** — the most reliable part of the reference.
- **Every documented listing filter works** (`locality`, `bhk`, `property_type`, price range, `furnishing`), individually and combined.
- **Default `limit` is 20**; **city scoping holds** — all 5,690 records are `city_id: 3`.
- **Ids are unique; `project_id` is null on resale** (1,461 of 3,800) with no orphans.
- **Rental money and areas are clean** — rent per sq.ft 22–60, `deposit/price` 2–10 months, no hidden bundling. "Correct prices and areas" for rentals and projects points at *projects*.
- **Project areas and dates are well-formed**; no project launches after the reference moment.
- **Rentals and projects contain zero corrupt records; rentals contain zero duplicates.**
- **Offset paging is stable** — re-fetching after a crawl returned byte-identical records.
- **`/health` is exactly what it claims to be.**
- **Hour-of-day can't reveal the timezone** — posting is uniform across the clock (CV 0.07/0.11), so that discriminator had no power.
- **The whole `magichomes` feed isn't sqm** — only 306 of 760 records are; detection is per-record.

## What I would do with another two days

1. Attack Q2 harder — a pairwise scorer over all records instead of blocking on ten exact fields (the ±1% tolerance is 32 properties wide).
2. Explain the 0.91215 `total` constant — page a tiny filter and watch how it rounds.
3. Chase the ~13-listing cluster in the last three hours before the reference moment (question-8 boundary).
4. Trigger the documented 403 and 429 paths to confirm or rule them out.
5. Cross-check `is_verified` (true on 85% of the fake set vs 62% overall).
